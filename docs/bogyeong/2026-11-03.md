## 1. 질문·답변 도착 정보 동기화 API 구현

브로커가 접속·재접속하거나 실시간 알림을 놓쳤을 때, 자신에게 도착한 질문·답변 정보를 다시 가져오는 API를 구현했다.

```http
GET /api/v1/agents/me/task-messages?cursor={nextCursor}&limit=50
```

### 조회 계약과 권한

- Agent Bearer 토큰으로 인증한다. 사용자 로그인 세션으로 대체하지 않는다.
- 인증된 Agent가 현재 팀의 Task 참여자이고, 작성자가 해당 Task의 상대 참여자인 이벤트만 반환한다.
- 본인이 작성한 메시지, 자기 배정 Task의 자기 질문, 비참여 Agent 작성, 다른 팀의 이벤트는 제외한다.
- 응답 항목은 `eventId`, `taskId`, `sequence`, `eventType`, `createdAt`이다. 본문은 기존 공통 상세 조회로 확인한다.
- 큰 정수의 JavaScript 정밀도 손실을 피하도록 `eventId`와 `sequence`를 문자열로 반환한다.
- `limit`은 기본 50, 허용 범위는 1~100이다. 응답에 `nextCursor`와 `hasNext`를 제공한다.
- Outbox의 존재·발행 성공 여부와 관계없이 원본 `task_events`를 조회한다. Task가 종료되어도 권한이 유지되면 복구할 수 있다.
- GET 요청으로 Task 상태·version·시각, 이벤트·Outbox·읽음 상태를 변경하지 않는다.

### develop V7 스키마와 cursor 정합성

- 기존 develop의 `V7__extend_task_events.sql` 및 공통 `TaskEvent` 계약에 맞춰 구현을 조정했다.
- 별도 수신함 테이블, 동기화 전용 DB 컬럼, 추가 마이그레이션은 만들지 않았다.
- 전역 마지막 eventId 대신 Task별로 실제 반환한 마지막 sequence를 cursor에 보존한다.
- 같은 Task의 이벤트 순서는 기존 V7의 부모 행 잠금으로 보장하고, 서로 다른 Task의 늦은 커밋은 개별 진행 위치로 복구한다.
- 빈 조회에서는 진행 위치를 앞당기지 않는다. Task를 순환 조회해 한 Task에 메시지가 몰려도 다른 Task가 계속 밀리지 않도록 했다.
- cursor는 gzip 압축 및 HMAC-SHA256 서명을 사용하며 Agent·사용자·팀 신원에 바인딩한다.
- 변조·손상된 cursor는 400, 다른 Agent의 정상 cursor는 403으로 처리한다.
- 운영 설정에 `TASK_MESSAGE_CURSOR_SECRET` 전달 경로를 추가했다. 서버 재시작·여러 인스턴스에서 동일한 키를 유지해야 한다.

## 2. 질문·답변 WebSocket 알림 발행 구현

기존 Outbox 발행기에 질문·답변 알림을 추가해, 상대 Agent의 브로커가 동기화 API를 즉시 조회할 수 있도록 했다.

```text
질문·답변 POST
→ TaskEvent와 Outbox를 같은 트랜잭션에서 저장
→ 커밋된 Outbox를 기존 발행기가 점유
→ 원본 이벤트·수신자·현재 소켓의 인증 정보 검증
→ 저장된 Outbox JSON을 상대 Agent의 WebSocket으로 전송
→ 브로커가 task-messages API로 원본 도착 정보 조회
```

### 알림 계약과 전송 대상

- `TASK_QUESTION_CREATED`, `TASK_ANSWER_CREATED`를 기존 발행 대상에 추가했다.
- 상태 변경·완료 알림은 기존처럼 요청자에게 보내고, 질문·답변 알림은 저장된 `receiver_agent_id`에 따라 상대 참여자에게 보낸다.
- `event_id`는 Outbox UUID이고, `payload.task_event_id`는 원본 TaskEvent ID다. 두 식별자의 역할을 구분했다.
- 알림에는 본문을 넣지 않는다. 브로커가 동기화를 시작하는 신호로 사용한다.
- 질문·답변은 Task 상태 변경이 아니므로 알림에 version을 요구하지 않는다. 기존 상태·완료 알림의 version 검증은 유지한다.
- 원본 이벤트의 Task·종류·sequence·작성자, 상대 참여자 여부, 현재 팀 소속과 소켓의 Agent·소유자·팀 인증 정보를 검증한다.

### 실패와 복구

- 기존 Outbox의 점유·점유 연장·재시도·시도 횟수 제한을 재사용한다.
- 연결 없음·교체·전송 오류는 기존 정책으로 재시도한다.
- 잘못된 원본 참조나 수신 대상은 `INVALID_EVENT`로 실패 처리한다.
- 재시도에서도 저장한 JSON과 event_id를 그대로 사용한다.
- `PUBLISHED`는 서버의 소켓 쓰기 성공이다. 브로커 ACK나 로컬 DB 저장 완료를 의미하지 않는다.
- 알림을 놓쳐도 브로커가 재접속·안전망 Pull로 원본을 복구할 수 있도록 REST 동기화와 역할을 분리했다. 실제 브로커의 타이머·로컬 저장 동작을 이 서버 구현만으로 검증한 것은 아니다.
- DB 스키마와 기존 V7 마이그레이션은 변경하지 않았다.

## 3. GitHub Actions 실행 시간 확인 및 빌드 캐시 적용

### 기존 설정 확인

- `.github/workflows/ci-cd.yml`의 `jobs.build.steps`에서 빌드·테스트를 실행하는 구조를 확인했다.
- `actions/setup-java@v4`의 `cache: gradle`은 이미 설정돼 있었다.
- 기존 Gradle 명령에는 `--build-cache`가 없어 컴파일 등 캐시 가능한 작업의 결과 재사용이 활성화되지 않은 상태였다.
- `jobs`가 폴더가 아니라 YAML 파일의 설정 항목이라는 점과 GitHub·IntelliJ에서 파일을 찾는 위치를 정리했다.

### 적용한 변경

커밋 `a6f602a`에서 다음 변경을 반영했다. 문서 작성 시점의 로컬 develop에도 해당 커밋이 포함돼 있다.

1. `setup-java`의 `cache: gradle` 제거
2. `gradle/actions/setup-gradle@v4` 추가
3. PR에서는 캐시를 읽기만 하고, develop/master push 실행에서는 저장도 하도록 설정
4. Gradle 빌드 명령에 `--build-cache` 추가

```yaml
- uses: gradle/actions/setup-gradle@v4
  with:
    cache-read-only: ${{ github.event_name == 'pull_request' }}

- name: Gradle build (통합 테스트 포함)
  run: |
    chmod +x gradlew
    ./gradlew build --no-daemon --build-cache
```

PR을 merge하면 대상 브랜치에 push 이벤트가 발생하므로, develop/master에 직접 push하지 않아도 캐시를 저장할 수 있다. PR에서 저장한 캐시는 해당 PR의 후속 실행으로 재사용 범위가 제한되므로, 대상 브랜치의 캐시를 중심으로 관리하도록 했다. PR 캐시 저장이 금지된 것은 아니다.

작업 브랜치는 `feature/infra/gradle-build-cache`이며, 추천한 커밋 형식은 `chore(infra): CI에 Gradle 빌드 캐시 적용`이다. 브랜치는 `{type}/{scope}/{description}`, 커밋은 `type(scope): message`라는 프로젝트 규칙을 기준으로 정리했다.

## 4. 확인한 성능 개선 후보와 남은 작업

### Spring 컨텍스트·DB 컨테이너 재사용

공통 `AbstractIntegrationTest`에 다음 설정이 있어 테스트 클래스가 끝날 때마다 Spring 컨텍스트를 폐기하는 구조를 확인했다.

```java
@DirtiesContext(classMode = DirtiesContext.ClassMode.AFTER_CLASS)
```

테스트 설정이 같은 클래스끼리 Spring 컨텍스트와 DB 컨테이너를 공유하면 초기화 비용을 줄일 여지가 있다. 다만 실제 병목으로 확정한 것은 아니며, 아래 변경은 이번 작업에 포함하지 않았다.

- 테스트 실행 전체에서 PostgreSQL 컨테이너를 공유하도록 수명 관리 변경
- 테스트 사이 DB 데이터·메모리 상태 초기화 보강
- 공통 `@DirtiesContext` 제거 및 필요한 테스트에만 제한적으로 적용

현재 JUnit 컨테이너 수명 관리 방식에서 `@DirtiesContext`만 제거하면 종료된 DB와 재사용된 Spring 컨텍스트의 수명이 어긋날 수 있으므로 함께 검토해야 한다.

### 후속 확인 사항

- 캐시를 채운 뒤 후속 실행에서 `FROM-CACHE`와 캐시 복원 여부를 확인한다.
- 적용 전후 동일 조건의 실행을 비교한다. 이번 기록에는 캐시 적용 후 단축 시간을 확정하지 않는다.
- 필요하면 Gradle 명령에 `--info`를 추가해 작업 진행과 캐시 사용 로그를 자세히 남긴다. `a6f602a`에는 이 옵션이 포함돼 있지 않다.
- 테스트 결과 캐시를 제외하는 `outputs.doNotCacheIf(...)`는 설명한 선택지이며 실제 `build.gradle`에 적용하지 않았다.
- 개별 테스트 시간·컨텍스트 시작 횟수·컨테이너 준비 시간을 확인한 뒤 추가 최적화 범위를 정한다.
