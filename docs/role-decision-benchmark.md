# 역할 결정 모델 도입 전후 벤치마크

담당 Agent 추천의 역할 태그 결정 모델([설명](agent-recommendation.md#역할-태그-결정-모델-보강-선택-기본-꺼짐))을 끈 상태(도입 전, 토큰 일치만)와 켠 상태(도입 후)를 같은 사례로 비교한 기록이다(S15P31D108-251, 2026-11-16).

수치는 모두 만든 사례로 잰 것이다. 실제 팀의 태그와 질문으로 잰 값이 아니므로 운영에서의 정확도를 보장하지 않는다. 아래 "한계"를 함께 읽는다.

## 요약

| 항목 | 도입 전 | 도입 후 (임계값 0.7) |
| --- | --- | --- |
| 태그 판정 정답 (253건) | 108 | 243 |
| 태그 판정 재현율 (일치해야 하는 148건) | 0.068 (10건) | 0.986 (146건) |
| 태그 판정의 틀린 일치 (일치하면 안 되는 105건) | 7건 | 8건 |
| 담당이 있는 질문 35건 중 담당을 찾은 질문 | 8 | 35 (담당만 추천 28, 다른 Agent와 함께 추천 7) |
| 담당이 없는 질문 10건 중 잘못 추천 | 0 | 1 |
| 추천 한 번에 더해지는 지연 | 없음 | 중앙값 634~686ms, p95 837~959ms |
| 추천 한 번의 모델 비용 (태그 약 22개) | 없음 | 약 0.0003달러 |

- 결정 모델은 토큰 일치가 놓치던 일치를 거의 모두 찾았다. 틀린 일치는 한 건 늘었다.
- 추천으로 보면 담당을 찾지 못하던 27건이 모두 담당을 찾았다. 대신 담당 외의 Agent가 함께 추천되는 경우가 7건 생겼고, 담당이 없는 질문 하나에 추천이 나왔다.
- 토큰 일치가 이미 틀리는 사례(7건)는 켜도 그대로다. 결정 모델은 일치를 추가만 하기 때문이다.

## 측정 방법

| 측정 | 사례 | 테스트 |
| --- | --- | --- |
| 태그 판정 | [`role-decision-eval.txt`](../src/test/resources/recommendation/role-decision-eval.txt) 253건(Y 148, N 105), 유형 10개 | `RoleDecisionEvaluationTest` |
| 추천 결과·지연 | [`role-decision-team.txt`](../src/test/resources/recommendation/role-decision-team.txt) Agent 8명, 질문 45건 | `RoleDecisionRecommendationBenchmarkTest` |

- 모델은 OpenRouter Decisions API의 `google/gemini-decision-1`, 임계값은 기본값 0.7이다. 측정 전에 따로 보낸 호출 한 번의 응답은 모델을 `google/gemini-decision-1-20261111`로 표기했다.
- 태그 판정은 질문마다 토큰으로 일치하지 않은 태그만 한 번에 묻는다(운영 경로와 같다). 도입 후의 판정은 토큰 일치와 모델 일치의 합집합이다.
- 추천 결과는 운영 코드의 추천 서비스를 그대로 쓰고, DB 조회와 Git 근거만 대체했다. Git 근거가 없는 상태라 역할 점수만으로 추천이 정해진다. 켠 상태는 세 번 반복했다. 제한 시간은 운영 기본값 1500ms다.
- 호출은 하나씩 차례로 보냈다. 부하 실험은 하지 않았다.
- 기본 테스트 실행은 실제 모델을 부르지 않는다. 세트의 형식과 유형별 토큰 일치 여부, 끈 상태의 추천이 토큰 일치만 쓰는지만 확인한다.

다시 재려면 OpenRouter 키를 환경 변수에 두고 실행한다. 태그 판정 한 번에 약 0.004달러, 추천 비교 한 번(켠 상태 3회 반복)에 약 0.04달러가 들었다.

```bash
DECISION_MODEL_EVAL=true DECISION_MODEL_API_KEY=<OpenRouter 키> \
./gradlew test --tests '*RoleDecisionEvaluationTest' --tests '*RoleDecisionRecommendationBenchmarkTest' -i
```

## 사례와 정답의 검토

사례는 이 기능을 만든 쪽(Claude)이 썼다. 편향을 줄이려고 Antigravity CLI(agy 1.4.12)의 `gemini-4-argon-medium`에게 독립 판정을 받았다. 검토자는 빈 폴더에서 실행했고, 정답과 유형을 가린 태그·질문 쌍만 무작위 순서로 받아 Y / N / 모호함으로 판정했다.

| 단계 | 대상 | 결과 |
| --- | --- | --- |
| 1차 판정 | 태그·질문 224쌍 | 220쌍 일치, 4쌍 모호함, 반대 판정 0 |
| 1차 판정 | 팀 질문 41건의 담당(이 질문들은 뒤에 모두 다시 썼다) | 41건 모두 맞음(담당을 둘로 적은 질문에 하나만 고른 경우 포함) |
| 세트 검토 | 두 파일 전체(정답 포함) | 아래 지적 |
| 2차 판정 | 새로 쓴 21쌍과 이미 일치한 12쌍 | 33쌍 모두 일치 |
| 2차 판정 | 다시 쓴 팀 질문 45건의 담당 | 45건 모두 같음 |

처리 기준은 판정 전에 정했다. 둘이 같게 판정한 사례만 채점에 쓰고, 모호하다고 한 사례는 뺐다.

- 뺀 4쌍: `모니터링|로그 파일 보관 기간 정책이 뭐야?`, `파일 업로드|다운로드 링크가 만료됐대`, `이미지|도커 이미지 빌드가 느려`, `풀스택|배포 파이프라인이 실패했어`.
- 세트 검토의 지적과 반영:
  - 켰을 때의 부작용은 틀린 일치로만 나타나는데, 그것을 재는 사례가 적고 무관한 조합은 너무 쉽다. → 여러 영역이 섞인 질문 20건(`multi-domain`)과 인접 영역 사례를 더했다.
  - 팀 질문 대부분이 평가 세트의 문장을 그대로 썼다. → 팀 질문 45건을 겹치지 않게 새로 썼다.
  - 팀의 "담당 없음" 질문이 업무가 아닌 잡담 위주다. → 업무 질문이지만 담당이 없는 질문 6건을 넣었다.
  - `로그 아웃`처럼 토큰 일치를 유도하려고 부자연스럽게 띄어 쓴 사례가 있다. → 자연스러운 문장으로 바꿨다.
  - 유형이 맞지 않는 사례가 있다. → 2건을 `unrelated`로, 약어 4건을 `cross-lingual`로 옮겼다.
- 검토자가 제안한 추가 사례 20건은 작성자가 따로 판정해 같게 본 13건만 넣었다. 나머지 7건은 작성자가 모호하다고 보아 넣지 않았다. 이 13건은 검토자의 정답을 본 상태에서 판정한 것이라 가린 판정이 아니다.
- 건수: 1차의 224쌍에서 4쌍을 빼 220쌍, 여러 영역이 섞인 질문 20쌍과 검토자 제안 13쌍을 더해 253쌍이다. 부자연스럽다고 지적된 1쌍은 새 문장으로 바꿨다.
- 순서: 두 차례 판정과 세트 확정을 마친 뒤에 결정 모델로 측정했고, 측정 결과를 본 뒤에는 사례와 정답을 바꾸지 않았다. 그 전에 결정 모델을 부른 것은 응답의 사용량 필드를 보려고 보낸 호출 한 번(태그 5개)뿐이다.

## 추천 결과

팀은 영역별 Agent 7명과, 무엇에나 맞는 태그(`모든 개발 질문`)를 단 Agent 1명이다. 켠 상태 세 번의 결과가 모두 같았고, 다시 실행한 결과도 같았다.

| 질문 | 결과 | 도입 전 | 도입 후 |
| --- | --- | --- | --- |
| 담당 있음 (35건) | 담당만 추천 | 8 | 28 |
| | 담당과 다른 Agent를 함께 추천 | 0 | 7 |
| | 다른 Agent만 추천 | 0 | 0 |
| | 근거 부족 (담당을 찾지 못함) | 27 | 0 |
| 담당 없음 (10건) | 근거 부족 (맞는 결과) | 10 | 9 |
| | 잘못 추천 | 0 | 1 |
| 전체 | 무엇에나 맞는 태그를 단 Agent 추천 | 0 | 0 |

- 끈 상태에서 담당을 찾은 8건은 질문에 태그가 그대로 들어 있는 경우다.
- 담당과 함께 추천된 다른 Agent 7건 가운데 4건은 `프론트엔드` 태그였다(예: `안드로이드 앱이 특정 기기에서 바로 꺼져요`에 모바일 담당과 프론트 담당). 나머지는 `인프라`·`배포` 2건, `모바일 앱` 1건이다. 넓은 계층을 가리키는 태그가 일치를 더 잘 끌어오는 것으로 보인다.
- 이 세트는 질문마다 담당을 한 명만 적었다. 함께 추천된 Agent 중에는 그 질문을 받아도 이상하지 않은 경우가 있다(FCM 발송 실패에 모바일 담당, Redis 메모리 부족에 인프라 담당, iOS 심사 반려에 배포 담당). 그래서 7건이 모두 결과를 흐린 것이라고 볼 수는 없다. 측정 뒤에 정답을 고치지 않으려고 그대로 두었다.
- 그 7건 중 1건은 끈 상태에서 담당만 추천하던 질문이다. `지도 줌 레벨 기본값을 바꾸고 싶어`는 끄면 모바일 담당 단독, 켜면 프론트 담당이 함께 추천된다. 켜서 결과가 흐려진 경우다.
- 잘못 추천 1건은 `추천 알고리즘 가중치를 바꾸고 싶어`에 `검색` 태그가 일치한 것이다. 태그 판정의 틀린 일치(`검색|추천 상품 목록이 비어 있어`)와 같은 방향이다.
- 이 비교에는 Git 근거가 없다. 운영에서는 Git 점수(최대 40점)가 더해져 동점이 갈릴 수 있으므로, "함께 추천"의 비율이 그대로 나타난다고 볼 수 없다.

## 지연과 비용

| 측정 | 호출당 태그 | 지연 중앙값 | p95 | 최대 | 입력 토큰 | 비용 |
| --- | --- | --- | --- | --- | --- | --- |
| 태그 판정 (180회, 2번 실행) | 평균 1.3개(1~4개) | 577~578ms | 726~792ms | 1332~1707ms | 평균 232 | 호출당 0.000023달러 |
| 추천 (135회, 2번 실행) | 평균 21.8개 | 634~686ms | 837~959ms | 1105~1235ms | 평균 3,026 | 추천당 0.000303달러 |

- 끈 상태의 추천은 이 측정에서 1ms 안팎이다. DB와 네트워크가 없어서 그렇고, 실제 추천 지연이 아니다. 위 값은 결정 모델 호출이 더하는 시간으로 읽는다.
- 응답을 받지 못한 호출은 없었다(추천 270회는 제한 시간 1500ms, 태그 판정 360회는 2000ms). 다만 태그 판정의 가장 느린 호출은 1707ms로 운영 제한 시간(1500ms)을 넘었다. 운영에서 제한 시간을 넘기면 그 추천은 끈 상태와 같은 결과가 된다.
- 호출당 태그가 평균 1.3개에서 21.8개로 늘어도 지연 중앙값은 0.06~0.11초 늘었다. 비용은 태그 수에 비례한다(태그 하나에 입력 토큰 약 140).
- 비용은 응답의 `usage`가 알려 준 값이다. 청구 비용과 제공자 원가 중 큰 값을 썼고, 이번에는 제공자 원가였다(입력 100만 토큰당 0.10달러, 출력 토큰 0). 추천 1,000회에 약 0.3달러다. 팀의 태그가 많아지면 그만큼 늘어난다.

## 한계

- **만든 사례다.** 실제 팀의 태그와 질문이 아니다. 문장이 짧고 한 가지를 묻는 경우가 많아 실제 질문보다 쉽다.
- **도입 전 수치는 세트 구성의 영향을 크게 받는다.** 일치해야 하는 148건 중 138건을 토큰으로는 일치하지 않게 골랐으므로, 재현율 0.068은 "토큰 일치가 현장에서 6.8%만 맞힌다"는 뜻이 아니다. 실제 질문에 태그 단어가 그대로 들어 있는 비율은 재지 않았다.
- **정답을 사람이 검토하지 않았다.** 작성자와 검토자가 모두 LLM이고, 검토자(Gemini 4 Argon)와 결정 모델(`gemini-decision-1`)은 같은 회사의 모델이다. 두 모델의 판단이 같은 쪽으로 기울어 있으면 도입 후 수치가 실제보다 좋게 나올 수 있다. 판정이 거의 모두 일치했다는 점은 사례가 분명한 것 위주라는 뜻이기도 하다.
- **지연은 PC 한 대, 한 시간대, 차례로 보낸 호출의 값이다.** 호출을 연달아 보내 연결을 재사용했다. 운영에서는 추천이 드물어 호출마다 연결과 TLS 설정을 새로 할 수 있으므로, 첫 호출의 지연은 위 중앙값보다 길 수 있다. 동시 요청이 있을 때의 지연과 OpenRouter의 호출 한도는 재지 않았다. MCP에서 브로커를 거쳐 중앙까지 가는 전체 경로의 지연도 이번에는 재지 않았다.
- **건수가 적은 항목은 비율로 읽지 않는다.** 담당 없는 질문의 잘못 추천 1건(10건 중), 인접 영역의 틀린 일치 1건(26건 중)은 그런 경우가 있다는 정도의 근거다.
- **정답에 이견이 남아 있다.** 커밋 전 교차검증(Claude Opus 5.5)은 다음 정답을 의심스럽다고 보았다: `품질 보증|QA에서 재현한 버그 좀 봐줘`(Y), `인증|OTP 인증번호가 안 와요`(Y), `권한|퍼미션 에러가 나요`(Y), `검색|추천 상품 목록이 비어 있어`(N), `알림|슬랙 배포 알림 웹훅 설정은 젠킨스 어디에 걸려 있어?`(N), `이미지|사진 업로드하면 깨져 보여요`(Y). 작성자와 검토자의 판정이 같았던 사례라 그대로 두었다. 이 가운데 두 건은 도입 후에 틀린 것으로 집계된 사례다.
- **모델이 바뀌면 결과가 바뀐다.** OpenRouter의 모델 ID가 가리키는 판은 날짜가 붙은 것(`-20261111`)이었다. 판이 바뀌면 다시 잰다.
- 한 요청에 함께 보낸 다른 태그가 판정에 영향을 주는지는 재지 않았다. 추천 비교에서 무엇에나 맞는 태그를 단 Agent는 추천되지 않았지만, 그 태그가 같은 요청의 다른 판정에 준 영향은 비교할 대상이 없어 알 수 없다.
